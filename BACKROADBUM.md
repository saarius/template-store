# Backroad Bum deployment

**Owner Steer1 (November10) supersedes local activation below.** Stop expanding/activating bespoke local transports; migrate to hosted DinkusKit with unmodified Registry plugins, then retire redundant local services after hosted verification or a concrete blocker. Prioritize the #211 cart PR under the pragmatic verification gate. Existing local controls stay disabled; older activation details are history/recovery, not the target plan.

Merchant branch: `backroadbum/store`, serving https://backroadbum.com. This is an explicit merchant composition, not a generic self-hosting release or upstream proposal. `PRODUCT.md` and `DESIGN.md` record the provisional brand; the original starter design is at `docs/template-design.md`.

## Current state
Five EmDash products, two collections, cart and field notes use Commerce-owned prices and availability. Public Stripe TEST checkout, same-browser paid receipts, manual demo fulfillment and webhook-driven background reconciliation are verified. Commerce runs the merchant TEST profile based on v0.8.0; Payments’ pinned Registry bundle and a merchant Ship sandbox profile are mounted; Ship automation and email/account recovery remain unconnected or unverified. The private Ship practice host runs on loopback8788 with intake closed. Ship’s authenticated native admin verifies that host, saves practice packing and supports one selected-order practice label/PDF. Production remains unselected and Commerce sends it no orders; synthetic tests are not live-store fulfillment proof. Source and activation prerequisites are in `../ship/ops/backroadbum/README.md`. Local recovery now includes its online SQLite copies and private configuration, with an isolated workerd restore drill.

## Ship recovery (local only)
The daily timer and every deploy call `ops/backroadbum/backup.py`. If the Ship directory exists, missing metadata, unreadable/corrupt SQLite, a linked input, non-0600 configuration or a configuration/storage-binding mismatch refuses the entire new archive and preserves older recovery points. Ship SQLite is copied through the online backup API, including committed WAL state; caches, raw WAL/SHM files and arbitrary service files are excluded. Archives stay0600 under the0700 backups directory, with at most three retained. **These archives now contain a private Ship print secret: never upload them to public artifacts or git.** Stripe, EmDash, Payments and browser credentials are not swept into the archive.

```sh
python3 -m unittest discover -s ops/backroadbum -p test_backup.py -v
# Ship’s workerd module paths require the peer repository as working directory.
(cd ../ship && node --test ../template-store/ops/backroadbum/test_ship_recovery.mjs)
# Build the peer Ship worker first if its ignored bundle is missing; see its README.
(cd ../ship && node ../template-store/ops/backroadbum/verify-ship-recovery.mjs /var/lib/backroadbum/backups/PRIVATE_ARCHIVE.tar.gz)
```

The drill extracts only allowlisted regular Ship files into a new0700 temporary directory, checks integrity/binding, starts the peer merchant host without provider/issuer network and checks restart plus anonymous-admin denial. It removes that copy in `finally`, never replaces production files, and is not proof of a real shipment. The reusable synthetic integration test separately proves an online copy of disabled single-order admission, a practice label, its still-valid PDF capability and pending event. Only the disposable restored copy is briefly re-enabled to inspect that event, then disabled again. Snapshot validation refuses a corrupt/missing admission row or foreign-order mismatch while accepting older snapshots without the additive table; no fixture order goes into production.

For an actual incident, stop Ship first and keep intake disabled. Run the isolated drill before restoring; replace the complete persistence namespace and matching configuration together under0700/0600 permissions, not individual database rows or generations. Do not restore stale WAL/SHM or merge another generation. Start Ship only after checking the binding and closed admission, then reconcile with canonical Commerce state before any subsequent admission. This is a narrow Ship runbook, not a verified full-store or off-host recovery procedure.

## Public request admission
Caddy must overwrite `X-Backroadbum-Client-IP` with `{remote_host}` in its store `reverse_proxy 127.0.0.1:4321` block. The listener is loopback-only; never trust browser-provided forwarding headers or expose it directly. Private Caddy credentials/configuration are deliberately not committed.

The merchant middleware checks same-origin JSON, method, bounded body and time before Commerce dispatch. Fixed ten-minute windows allow per-network/store-wide: prepare8/80, start3/20, status120/1200. Both status paths share the status budget. HTTP429 includes Retry-After and preserves the cart; existing receipts have a separate budget from starts. These are request counts, not payments or visitor analytics; conservatively counting a refused/replayed start is intentional.

Operational counters live in `/var/lib/backroadbum/admission.db`0600. `/etc/backroadbum/admission.key`0600 holds a private32-byte HMAC key. No raw IP is kept: keys include the window, and old rows are purged on the next admitted checkout request. Atomic global/peer counters survive server restart; key/storage/clock errors fail closed. This database is not a competing order model and is not included in commerce recovery snapshots; restoring/rekeying can reset request budgets but cannot authorize payment or change paid data.
